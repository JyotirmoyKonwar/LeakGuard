# Dataset card

**All data comes from existing Hugging Face datasets. No synthetic text was generated for this project.** Some source datasets were themselves created synthetically by their authors; that is noted below. The pipeline is `src/leakguard/datagen/hf.py`, run as `make data`.

## Sources

| Source | Used for | Rows used | License | Notes |
|---|---|---|---|---|
| [`ai4privacy/open-pii-masking-500k-ai4privacy`](https://huggingface.co/datasets/ai4privacy/open-pii-masking-500k-ai4privacy) | PII spans in 8 languages (en, fr, de, es, it, nl, **hi**, **te**) | 6,000 (balanced by language) | ai4privacy licence (free for research / non-commercial; check the card for commercial use) | Generated by the dataset authors; character-level spans |
| [`Podric/prowl-secrets-corpus`](https://huggingface.co/datasets/Podric/prowl-secrets-corpus) | Secrets in code, Slack, Jira, Confluence and logs, plus **13 kinds of look-alike negatives** | about 6,000 texts (every row of each sampled text) | CC-BY-NC 4.0 | 31 credential types; negatives such as UUIDs, hashes, git SHAs, hex colours, placeholders, example keys and near-misses |
| [`deepset/prompt-injections`](https://huggingface.co/datasets/deepset/prompt-injections) | Injection vs benign prompts (en + de) | 662 | Apache 2.0 | Original test split kept as test |
| [`v1adam/Prompt_injection_and_Sensitive_Data_exposure_detection`](https://huggingface.co/datasets/v1adam/Prompt_injection_and_Sensitive_Data_exposure_detection) | Benign / sensitive / jailbreak prompts (decision-level) | 1,000 | Apache 2.0 | No spans, so used only for action-level metrics |
| [`nisaefendioglu/synthetic-sensitive-data-in-source-code-n300`](https://huggingface.co/datasets/nisaefendioglu/synthetic-sensitive-data-in-source-code-n300) | Source code with multiple secrets + PII, used as **tool payloads** | 300 | MIT | No spans; dev/test only |

Not used: `Syghmon/gloom-data-exfiltration-v2`. It has agent transcripts labelled for covert exfiltration, but they average 56k characters, which is above the guard's input limit. It is listed as future work.

## Label mapping

* **ai4privacy → LeakGuard:**
  * GIVENNAME / SURNAME → PERSON (adjacent spans merged)
  * EMAIL; TELEPHONENUM → PHONE
  * STREET / BUILDINGNUM → ADDRESS
  * CREDITCARDNUMBER → CREDIT_CARD; PASSPORTNUM → PASSPORT
  * IDCARDNUM / TAXNUM / SOCIALNUM / DRIVERLICENSENUM → GOV_ID
  * **Ignored** (quasi-identifiers, not leaks on their own): CITY, TIME, DATE, TITLE, AGE, ZIPCODE, SEX, GENDER.
* **prowl → LeakGuard:** 31 credential types are mapped one-to-one where possible (for example `aws_access_key_id` → AWS_ACCESS_KEY). `generic_api_key` and `generic_high_entropy` → GENERIC_SECRET; `generic_password` → PASSWORD; `gcp_service_account` → PRIVATE_KEY. `neg_*` rows are negatives. `neg_pii` texts are dropped, because they are "negative for secrets" but still contain personal data, so they aren't clean negatives for a DLP guard.
* **prowl grouping:** a text appears in several rows, each labelling one value. The pipeline samples *texts*, then collects **every** row for those texts and unions their spans. An earlier version sampled rows and left real secrets unlabelled; this was found during error analysis (see `docs/report.md`).

## Gold actions (the specification)

Gold actions are a fixed function of each dataset's **own labels**, plus the direction and destination assigned to the row (`gold_for` in `hf.py`). They are **not** produced by running LeakGuard.

| Direction / destination | Gold |
|---|---|
| prompt → external | private key or DB URL → `block`; any other secret or PII → `redact`; ≥ 8 PII values → `escalate`; nothing → `allow` |
| prompt → internal LLM | only low-risk PII (name, email, phone, address) → `allow`; high-risk PII → `redact` |
| response | any secret → `block`; any PII (which the user never supplied) → `redact`; nothing → `allow` |
| tool payload → external | any secret or high-risk PII → `block`; only low-risk PII → `escalate`; nothing → `allow` |
| deepset / v1adam | injection or jailbreak → `block`; benign → `allow`; sensitive (no spans) → `protect` (anything but allow) |
| code dataset | any secret category → `block`; PII → `protect`; `internal_url` → `allow` (out of scope) |

**Direction re-use:** to test the response guard and the tool-payload guard without writing new text, a deterministic hash of the row ID assigns some rows to another direction:

* ai4privacy: 12% response, 10% internal LLM.
* prowl: 15% external tool payload, 10% response.

The text itself is never modified.

## Splits and reproducibility

* Splits are 60 / 20 / 20 train / dev / test, by a SHA-256 hash of the example ID, so they are stable across rebuilds. deepset keeps its own test split.
* `data/processed/manifest.json` records the seed, per-split SHA-256 hashes, and counts by source, scenario, gold action and language.
* **train** is not used by the current system: both models run zero-shot. It is kept so the splits stay stable if a model is trained later.
* **dev** is used for every threshold, rule and filter change.
* **test** is used only for the final numbers.

Current build (seed 42): train 8,152 · dev 2,921 · test 2,889 examples. The test split has 34 entity types and 8 languages.

## Known limitations

* **Prowl's gold labels cover secrets only.** Names inside its chat logs (for example "alice:") are unlabelled, so flagging them counts as a false positive. This inflates the false-block rate for prowl rows sent as responses or tool payloads.
* **No dataset supplies `escalate` gold labels in practice.** No ai4privacy prompt has ≥ 8 values, and contact-only tool payloads come only from re-used rows. Escalation is therefore reported as a *rate*, not as accuracy.
* **Credit card numbers in ai4privacy don't pass the Luhn check,** so the checksum validator correctly rejects them as cards. Only GLiNER can recall them, and this lowers measured recall for that entity.
* **Secrets coverage is limited** to the types the source datasets contain, as accepted when choosing Hugging Face-only data.
